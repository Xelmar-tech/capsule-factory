# Scribe — shared HTML artifact writer

The job: take structured content from a caller and emit a single self-contained HTML file in a consistent house style. Modern, clean, blog/article feel — readable as a document, not styled like a dashboard. Every artifact kind shares the same shell (header, breadcrumb, body, footer) and the same typography; only the body schema varies.

This skill is **the marketplace's design system**. Do not template HTML in other skills — call scribe instead. Adding a new document kind means extending scribe's schema list, not forking the template.

## Input contract

Callers invoke this skill with two arguments:

1. **`kind`** — one of: `status-report`, `verify-report`, `security-finding`, `threat-model`, `epic-overview`.
2. **`payload`** — a YAML/JSON document matching the schema for that kind (defined below).

If `kind` is unknown, refuse. Adding a new kind goes here, not in the caller.

## Common shell (every kind)

Every emitted HTML file shares this outer structure:

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8" />
  <meta name="viewport" content="width=device-width, initial-scale=1" />
  <title>{{ title }} — Capsule Factory</title>
  <style>
    /* House style: see "Style" section below. Inline, no external CSS, no JS. */
  </style>
</head>
<body>
  <header>
    <div class="breadcrumb">{{ kind }}</div>
    <h1>{{ title }}</h1>
    <div class="meta">
      <span>{{ generated_at }}</span>
      <span>{{ source_label }}</span>  <!-- e.g. "Linear cycle 14" or "PR #123" -->
    </div>
  </header>
  <main>
    {{ body }}  <!-- per-kind content -->
  </main>
  <footer>
    Generated by Capsule Factory — <code>{{ kind }}</code> schema v{{ schema_version }}.
  </footer>
</body>
</html>
```

Self-contained: no external assets, no JavaScript, no analytics. The HTML must work offline and open identically when emailed or pasted into a Notion page.

## Style

The visual target is "well-typeset article", not "dashboard." Specifics:

- **Type** — system sans (`-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, sans-serif`). Body 16px, line-height 1.55. Headings: H1 28px, H2 22px, H3 18px. Generous spacing, not cramped.
- **Width** — main column max-width 720px, centered, generous left/right padding. Reading-line discipline matters more than maximizing real estate.
- **Color** — neutral light theme by default: `#fafafa` page, `#111` body text, `#555` meta, `#0066cc` links, status colors (`#16a34a` ok / `#ea580c` warn / `#dc2626` crit) used sparingly. Dark mode via `prefers-color-scheme: dark` swapping to `#0e0e0e` / `#e8e8e8` / `#8ab4ff`.
- **Tables** — full-width within the column, zebra striping every other row, borderless except a thin bottom rule per row. Right-align numeric columns.
- **Code/identifiers** — `Menlo, Consolas, monospace` 14px, subtle background fill. Ticket IDs, PR numbers, file paths, env-var keys all rendered as `<code>`.
- **No emoji in the chrome.** Status is conveyed by color + text label (`OK`, `Warn`, `Crit`), not 🟢🟡🔴.

If you find yourself wanting a chart, embed a minimal inline SVG. Do not pull in any chart library.

## Per-kind body schemas

### kind: `status-report`

Payload:

```yaml
title: "<team> — <window>"
generated_at: <ISO timestamp>
window: "<human-readable>"      # e.g. "Cycle 14 (day 6 of 14)"
summary:
  opened: <N>
  closed: <N>
  in_progress: <N>
  net: <signed N>
sections:                        # rendered in this order
  - heading: "Epics in flight"
    items:                       # each item -> table row
      - id: "<linear-id>"
        title: "<epic title>"
        owner: "<linear handle or 'unassigned'>"
        state: "<state>"
        url: "<linear-url>"
  - heading: "Closed this window"
    items: [{id, title, owner, state, url}]
  - heading: "In progress"
    items: [{id, title, owner, state, url}]
  - heading: "Blocked"
    items: [{id, title, owner, state, url}]
  - heading: "Owner-less tickets"
    items: [{id, title, state, url}]
slack_summary: "<3–5 bullets as plain markdown>"  # not rendered in HTML, returned separately
```

Body layout: H2 "Summary" with a 4-cell metric strip (opened / closed / in progress / net), then each `section` as H2 with a table.

### kind: `verify-report`

Payload:

```yaml
title: "Verify — PR #<n>: <pr-title>"
generated_at: <ISO timestamp>
pr_url: "<github-url>"
claims:                          # each claim -> a section
  - claim: "<what the PR says it does>"
    method: "<what the verifier did to test it>"
    observed: "<what actually happened>"
    verdict: "ok" | "warn" | "crit"
    evidence:                    # optional
      - kind: "screenshot" | "video" | "log" | "snippet"
        ref: "<relative path or URL>"
        caption: "<optional>"
overall_verdict: "ok" | "warn" | "crit"
notes: "<free text>"             # optional
```

Body layout: H2 overall verdict (color-coded), then each `claim` as H3 with a 3-cell strip (Claim / Method / Observed) and embedded evidence (img/video/<pre>) below.

### kind: `security-finding`

Payload:

```yaml
title: "Security scan — <scope>"
generated_at: <ISO timestamp>
scope: "<pr | commit | path>"
findings:
  - severity: "crit" | "high" | "med" | "low" | "info"
    title: "<short>"
    file: "<path:line>"
    description: "<what's wrong>"
    rationale: "<why it matters in this codebase>"
    fix: "<concrete fix>"
summary:
  crit: <N>; high: <N>; med: <N>; low: <N>; info: <N>
```

Body layout: H2 summary table by severity, then findings grouped by severity (highest first) as H3 each.

### kind: `threat-model`

Payload:

```yaml
title: "Threat model — <system or feature>"
generated_at: <ISO timestamp>
system: "<name>"
assets: ["<asset>", ...]         # what we're protecting
boundaries: ["<boundary>", ...]  # trust boundaries
adversaries: ["<adversary>", ...]
threats:
  - category: "S" | "T" | "R" | "I" | "D" | "E"  # STRIDE
    description: "<threat>"
    likelihood: "high" | "med" | "low"
    impact: "high" | "med" | "low"
    mitigation: "<concrete mitigation>"
```

Body layout: H2 Assets / Trust boundaries / Adversaries as three bulleted lists, then H2 Threats with a STRIDE matrix table.

### kind: `epic-overview`

Payload:

```yaml
title: "Epic — <epic title>"
generated_at: <ISO timestamp>
epic_id: "<linear-id>"
epic_url: "<linear-url>"
goal: "<the goal sentence>"
scope:
  in: ["<item>", ...]
  out: ["<item>", ...]
acceptance: ["<criterion>", ...]
team:
  - role: "epic-conductor" | "implementer" | "analyst" | "qa-capture" | "debug-guru"
    status: "active" | "idle"
    last_action: "<what they did last>"
tickets:
  - id: "<linear-id>"
    title: "<ticket-title>"
    owner: "<agent role or human handle>"
    state: "<state>"
    url: "<linear-url>"
decisions:                       # the running decision log
  - at: "<ISO timestamp>"
    by: "<role>"
    decision: "<what was decided>"
    reason: "<why>"
```

Body layout: H2 Goal, then a strip of Scope / Out / Acceptance, then H2 Team (table), H2 Tickets (table grouped by state), H2 Decisions (chronological list).

This is the **living document** for an active epic — epic-conductor updates and re-emits it each time the team's state changes.

## Output contract

Return:

1. **`html`** — the rendered HTML string
2. **`slack_summary`** — for `status-report`, the paste-ready bullets (else empty)
3. **`path`** — the suggested destination path (`reports/YYYY-MM-DD-<kind>.html`)

The caller (pm-reporting, qa-capture, etc.) writes to disk. This skill does not perform I/O.

## Schema versioning

Bump `schema_version` (footer) when the payload contract changes incompatibly. Old reports remain readable since they're self-contained HTML.

## What this skill does NOT do

- Does not write to disk. Returns the HTML string; caller writes.
- Does not fetch data. The payload is fully formed when scribe is called.
- Does not handle markdown reports. If a caller wants markdown, they format it themselves — scribe is for HTML only.
- Does not include external assets. Inline CSS, inline SVG, embedded base64 if absolutely necessary. No CDN links.
